# Phase 22 — Benchmarking

**Purpose: measure and report only. No optimization changes were made in this phase** (per the roadmap's own rule) — these numbers are the honest baseline Phase 23+ will compare against.

No CPU-vs-GPU comparison: this project runs CPU-only by deliberate choice (Phase 2). `docs/phase1_inspection_report.md` has the original hardware context.

Full raw results: `docs/benchmark_results.json` (regenerated by `scripts/benchmark.py` — machine/load-dependent, not meant to be committed as a frozen record, only the discussion below is).

## Inference benchmark (real trained checkpoint, `checkpoints/phase13_run.pt`, 821,248 params)

| max_new_tokens | first_token_ms | total_ms | tokens/sec |
|---:|---:|---:|---:|
| 20 | 3.9 | 75.7 | 264.7 |
| 100 | 3.7 | 544.7 | 183.0 |
| 300 | 3.9 | 2377.8 | 126.0 |

Load time: 0.404s. Available system memory: 881MB → 872MB (a ~9MB footprint for a model this size — unsurprising for 821K fp32 params, ~3.3MB of weights plus normal Python/PyTorch overhead).

**The interesting finding, and why it's expected, not a bug**: first-token latency stays flat (~3.7-3.9ms) regardless of how much will eventually be generated — that's just the cost of one forward pass on the prompt. But **steady-state tokens/sec falls as generation gets longer** (265 → 183 → 126). This is the direct, predictable cost of not having a KV cache: at every single step, the model recomputes attention over the *entire context generated so far*, from scratch, because nothing from the previous step's attention computation is reused. As the sequence grows toward `context_length` (128), each step gets more expensive, so the *average* tokens/sec over a longer generation is dragged down by its later, costlier steps. A KV cache (explicitly a Phase 35 topic) would fix exactly this, by reusing each prior step's key/value projections instead of recomputing them — turning per-step cost from "proportional to sequence-length-so-far" into "roughly constant." This benchmark is what makes that a measured, motivated future improvement instead of a guess.

## Compute-cost benchmark (fresh untrained models — measures compute, not output quality)

| batch_size | context_length | params | step_ms | tokens/sec |
|---:|---:|---:|---:|---:|
| 8 | 64 | 813,056 | 53.8 | 9,508.5 |
| 32 | 64 | 813,056 | 195.8 | 10,457.4 |
| 8 | 128 | 821,248 | 128.2 | 7,988.9 |
| 32 | 128 | 821,248 | 451.4 | 9,073.9 |
| 32 | 256 | 837,632 | 1,143.3 | 7,165.5 |

Two clean, expected patterns:
- **Larger batch improves throughput efficiency** (batch 8→32 at context=64: 9,509 → 10,457 tokens/sec) — fixed per-call Python/PyTorch overhead gets amortized across more examples per call.
- **Larger context_length reduces tokens/sec** (context 64→128 at batch=8: 53.8ms → 128.2ms, more than 2x for a 2x context) — self-attention's cost grows faster than linearly with sequence length (each of T positions attends to all T positions, an O(T²) term), so doubling context costs more than doubling compute.

(Param counts differ slightly across context_length rows because the positional embedding table's size is `context_length × embedding_dim` — this is expected, not a bug: `128 × (128-64) = 8,192`, exactly the observed 821,248 − 813,056.)

## What this does — and doesn't — justify doing next

This data makes a concrete, measured case for KV caching as a high-value future optimization (Phase 35/36) — it directly targets the exact cost pattern observed here. It does **not**, on its own, justify any change right now: this phase's entire job was measuring honestly, not reacting to the numbers with code changes.
